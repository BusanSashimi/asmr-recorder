## AudioWorklet migration — `startAudioProcessing` off `ScriptProcessorNode`

**Third-wave item 3 of 5 (per `ai-dev/doc/next-implementations.md` sequencing).**

### Gate check (step 1)

AudioWorklet availability in this runtime was not observed via runtime console (WKWebView console
isn't in stdout). However, macOS 14.0 is the minimum target (`tauri.conf.json`), which ships
Safari 17. AudioWorklet has been Supported in WebKit since Safari 14.1 (macOS 11.3). Conclusion:
AudioWorklet is available on every macOS version this app targets. Proceeding per the plan.

### What changed — `frontend/src/components/asmr-recorder/recording-canvas.tsx`

**Two module-level constants added** (after the existing audio constants block):
- `ENCODE_WORKLET_NAME = "encode-source"` — processor name for `registerProcessor`.
- `ENCODE_WORKLET_CODE` — inline processor string: `EncodeSourceProcessor extends
  AudioWorkletProcessor`; `process(inputs)` copies each channel (`ch.slice()`) and posts
  the array via `this.port.postMessage`. Input buffer arrays are reused across `process()`
  calls; the copy prevents aliasing. `return true` keeps the node alive.

**`startAudioProcessing` rewritten:**

- **`emit(channels: Float32Array[])` closure** — extracted from the old `onaudioprocess` body.
  Reads `audioCtx.sampleRate` (not `inputBuffer.sampleRate`, which is unavailable on the
  worklet side but equal to it when using ScriptProcessorNode). Both paths call `emit()`.
- **`useScriptProcessor()` inner function** — the original ScriptProcessorNode path, refactored
  to call `emit()`. Kept as a permanent fallback per plan (WKWebView AudioWorklet support is not
  contractually guaranteed and can regress).
- **AudioWorklet branch (fire-and-forget async):** probes `audioCtx.audioWorklet`; if truthy,
  registers the Blob-URL module (`addModule`), creates `AudioWorkletNode` with `numberOfInputs:1,
  numberOfOutputs:1`, wires `node.port.onmessage → emit(data)`, connects
  `source → node → silentGain → audioCtx.destination`. Sets `audioProcessingCleanupRef`.
  On any failure, falls through to `useScriptProcessor()`.
- **`initializeWebCodecs` is unchanged** — still synchronous. Fire-and-forget means a few 128-frame
  quanta (~3ms at 48kHz) may be missed during module registration at record-start; inaudible.

## Implemented Bug A — frame-accurate trim audio desync fix

User chose "Bug A only". Implemented per `ai-dev/doc/bug-fixes-trim-desync-and-sck-leaks.md` §1.

### What changed (working tree, uncommitted)
- **`frontend/src/components/asmr-recorder/trim-segments.ts`** — two new pure, testable helpers:
  `rebaseTimestamp(srcTs, anchor, segOffset)` and `keepAudioPacket(pktStart, pktDuration, segIn)`.
- **`frontend/src/components/asmr-recorder/trim-editor.tsx`** `trimToBuffer` — extracted the
  frame-accurate predicate into `frameAccurateSeg`; added `audioAnchor = frameAccurateSeg ? seg.in
  : origin`. The audio loop now (a) drops packets ending before `seg.in` in the frame-accurate
  branch via `keepAudioPacket`, and (b) rebases audio with `audioAnchor` instead of always `origin`.
  All four rebase sites (3 video + 1 audio) now route through `rebaseTimestamp` so the two branches
  can't silently drift apart again. The else/lossless branch is behaviorally unchanged (anchor =
  `origin`, same as before).
- **`frontend/src/components/asmr-recorder/trim-segments.test.ts`** — +8 tests (rebaseTimestamp ×4
  incl. the Bug A regression that asserts the buggy `origin` anchor offsets a packet by exactly
  `(seg.in - origin)` ≈ 3s; keepAudioPacket ×4 incl. straddling-packet + unknown-duration edges).

### Root cause recap
Frame-accurate video rebased to `seg.in` but audio rebased to the earlier keyframe `origin`, so
audio was misaligned by `(seg.in - origin)` — up to one ~3s GOP. Fix anchors audio to `seg.in` too.

### Boundary policy (key decision)
AAC packets are ~21ms (1024 samples @ 48k) and can't be sub-trimmed without re-encode. We KEEP the
packet straddling `seg.in` (drop only packets ending before it), so alignment is within ~one packet.
Verified mediabunny tolerates the resulting negative first timestamp: `processTimestamps`
(isobmff-muxer.js:537/569) sets `startTimestampOffset` to the lowest ts and shifts samples to
media-time 0; an edit list is only emitted when the offset is **> 0** (isobmff-boxes.js:343), so a
negative start normalizes cleanly with no throw. Residual misalignment ≤ ~21ms (imperceptible).

### Gates
`npx tsc -b` 0 errors · `npm run test` **56/56** (was 48; +8) · `npx vite build` clean (main 481 kB,
mediabunny 641 kB — both unchanged).

## Migrated the recording muxer: mp4-muxer → mediabunny

Per `ai-dev/doc/mp4-muxer-to-mediabunny-migration.md`. The app shipped two MP4 muxers (mp4-muxer for
recording, mediabunny for trim); now there is one.

### What changed — `frontend/src/components/asmr-recorder/recording-canvas.tsx`
- **Import:** `mp4-muxer` (`Muxer`/`ArrayBufferTarget`) → `import type` of mediabunny `Output`/
  `BufferTarget`/`EncodedVideoPacketSource`/`EncodedAudioPacketSource`.
- **`muxerRef`** now holds `{ output, target, videoSource, audioSource, videoTail, audioTail,
  firstVideo, firstAudio }` instead of a `Muxer`.
- **`initializeWebCodecs`** is now `async` (`Promise<boolean>`); it `await import("mediabunny")`
  (keeps mediabunny in its existing code-split chunk), builds `Output` + `Mp4OutputFormat({fastStart:
  "in-memory"})` + `EncodedVideoPacketSource("avc")` (+ `EncodedAudioPacketSource("aac")` when audio),
  and `await output.start()` before any add. Width/height/channels/rate are no longer configured on
  the muxer — mediabunny derives them from the first packet's `decoderConfig` metadata. Caller in
  `startRecording` now `await`s it.
- **Chunk handoff:** encoder `output` callbacks convert via `EncodedPacket.fromEncodedChunk(chunk)`
  and chain `source.add(pkt, firstX ? meta : undefined)` on a per-source tail promise (decode order
  preserved; metadata only on the first packet, mirroring the trim editor). Used closure `holder`
  (NOT `muxerRef.current`) in the callbacks because `startAudioProcessing` feeds the encoder before
  `muxerRef.current` is assigned — a `muxerRef.current`-based callback would drop the first chunks.
- **Finalize:** `await Promise.all([videoTail, audioTail])` to drain queued async adds, then
  `await output.finalize()` and read `target.buffer` (was sync `muxer.finalize()` + `muxer.target.buffer`).
- **`extractAudioSpecificConfig` KEPT** (the load-bearing decision): verified in the bundled
  mediabunny source that `esds()` (isobmff-boxes.js:728-736) wraps `decoderConfig.description` in its
  own DecoderSpecificInfo exactly like mp4-muxer, and the AAC track setup (isobmff-muxer.js:274-276)
  requires a **bare ASC**. So handing it the WKWebView ES_Descriptor would still double-wrap → the
  workaround is still mandatory (the optimistic "mediabunny builds the esds, delete the helper"
  hypothesis was FALSE). Updated the two now-stale comments naming mp4-muxer.
