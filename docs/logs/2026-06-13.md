## Stage A optimization of the 4-way split recording pipeline

### Context / investigation
Asked to find a more optimal way to record the 4-way (2x2) split screen, starting
from `ai-dev/dev-logs/fixing-screen-recording-issue.md`. Key reframe: that dev log
documents the **native** SCK path (`screen_macos.rs`/`compositor.rs`/`encoder.rs`/
`manager.rs`), which only does screen + single webcam PiP and is largely dormant in
release builds (the `ffmpeg` cargo feature is only enabled by `dev.sh`). The actual
2x2 recording is done entirely in the browser: `preview.tsx` (4 MediaStreams + per-
section rAF crop canvases) → `recording-canvas.tsx` (2D-canvas composite + WebCodecs
H.264 + mp4-muxer, whole file in RAM) → base64 over `invoke("save_media_recording")`
→ Rust decode + `fs::write` (`lib.rs`).

Ran a multi-agent audit + adversarial verification. Findings & recommended path
(A now, C later; skip B/E; defer D) are summarized in chat. Two audit claims were
**refuted/corrected** by verification and should NOT be acted on as written:
- H.264 `avc1.42001f` (Baseline L3.1) does **not** break recording at 1440p60 —
  WKWebView/VideoToolbox uses the string only to pick the profile and applies
  `Baseline_AutoLevel`, so it encodes fine. Baseline *profile* is only a ~10-20%
  efficiency nicety, not a functional bug.
- `autoGainControl:false` is **not honored** by WebKit (bug 204444 still open);
  `channelCount:2` is unreliable on macOS Safari. `echoCancellation:false` (and
  effectively `noiseSuppression`) **are** honored.

### Changes made (all in `frontend/src/components/asmr-recorder/recording-canvas.tsx`)
1. **Audio constraints (ASMR quality).** `acquireAudioTrack` mic capture now passes
   `{ echoCancellation:false, noiseSuppression:false, autoGainControl:false,
   channelCount:2, sampleRate:48000 }` instead of `{ audio:true }`. Constants
   `AUDIO_NUM_CHANNELS 1→2` (stereo) and `AUDIO_BITRATE 128_000→256_000`. Added a
   `getSettings()` readback that warns when DSP stayed on or the mic fell back to
   mono (both expected on some WebKit builds — observable instead of silent).
2. **Dropped `willReadFrequently:true`** on the composite canvas (verified safe — no
   `getImageData`/`readPixels`/`toDataURL` anywhere). Hoisted the 2D context into
   `ctxRef` (created once, lazily) with `{ alpha:false }`. In WebKit that flag forces
   permanent software rasterization; removing it keeps the composite GPU-backed.

### Verification
- Adversarially reviewed the audio change end-to-end: channel-count is **coherent**
  (ScriptProcessorNode forces 2-ch input, so AudioData/encoder/muxer always agree).
- `npx tsc -b`: no errors in `recording-canvas.tsx`. `npx vite build`: succeeds.
- Pre-existing tsc errors (NOT from this work): `browser-recorder.tsx` missing
  `@tauri-apps/plugin-dialog`/`plugin-fs`, unused `HANDLE_SIZE` in
  `region-selector.tsx`, unused `SectionConfig` in `recording-context.tsx`.

### Known / deferred (not done this session)
- **Sample-rate divergence (latent, pre-existing):** `AudioData` uses
  `inputBuffer.sampleRate` while the encoder is configured at `AUDIO_SAMPLE_RATE`;
  if WebKit clamps the AudioContext to hardware rate they diverge and `encode()` can
  throw / pitch-skew. Worth fixing in a follow-up (use the constant for both).
- **No `AudioEncoder.isConfigSupported()` check:** if the stereo/256k AAC config is
  rejected, the catch tears down the *whole* video pipeline → silent WebM fallback.
  256k stereo AAC-LC is well within spec so unlikely, but the failure mode is
  disproportionate; consider isolating the audio-encoder setup in its own try/catch.
- Remaining Stage A items not yet started: direct source-rect cropping in
  `drawSection` (eliminate rAF crop loops), stream MP4 to disk via raw-binary Tauri
  IPC instead of base64, check `encodeQueueSize` for backpressure.

## Stage A continued — backpressure + direct cropping

### Changes
3. **Encoder backpressure** (`recording-canvas.tsx`). Added `ENCODE_QUEUE_LIMIT = 2`
   and `droppedFrameCountRef`. In `updateFrame`, when the WebCodecs path is active and
   `encoder.encodeQueueSize > ENCODE_QUEUE_LIMIT`, skip the composite+encode tick and
   count the drop (reported in the per-30-frame log). Guarded by `useWebCodecsRef` so
   it never affects the MediaRecorder fallback. Reset on recording start.
4. **Direct source-rect cropping** (`recording-canvas.tsx` + `preview.tsx`). For

   CSS cropping was judged a fragile, larger UX change for little extra gain, so the
   rAF loop is intentionally retained for display only.

### Verification + review-driven fix
- Adversarial review: **cropping correct, no issues** (coordinate-space neutral, no
  double-crop in the fallback, no stale-region/crash path, preview intact).

## Runtime verification of recorded output + audio esds fix

### What was verified
Inspected the first real recording (`test-results/recording_20260613_155040.mp4`).
- **Video PASS:** correct 2x2 composite (screen top-L/R, webcam bottom-L/R), 2560x1440,
  H.264 Constrained Baseline, 400 frames / 14.14s ≈ 28.3 fps (target 30). The Stage A
  video changes (willReadFrequently drop, direct cropping, backpressure) produced valid,
  visually-correct output.
- **Audio FAIL (root-caused):** the AAC track was undecodable — ffmpeg AND Apple
  CoreAudio (`afinfo`) both refused it ("Audio object type 0… 22050 Hz, 0 channels").
  Parsed the raw MP4 boxes: the `mp4a` header was correct (2ch/48kHz) and the real
  AudioSpecificConfig `0x1190` (AAC-LC/48k/stereo) was present **but buried one level too
  deep** — the `esds` was double-wrapped. Root cause: WKWebView/Safari's `AudioEncoder`
  emits `decoderConfig.description` as a full MPEG-4 ES_Descriptor, and mp4-muxer wraps
  whatever it's given in its own DecoderSpecificInfo (confirmed in mp4-muxer source:
  `esds` writes `description` verbatim as the tag-0x05 payload). So a standards parser
  reads the top byte (0x03) as audioObjectType → 0 → undecodable. Structural, independent
  of channel count/bitrate → NOT caused by the Stage A audio constants; it was latent.

### Fix (`frontend/src/components/asmr-recorder/recording-canvas.tsx`)
Added module-level `extractAudioSpecificConfig(description)`: walks the MPEG-4 descriptor
tree (ES_Descriptor 0x03 / DecoderConfigDescriptor 0x04) to the DecoderSpecificInfo
(0x05) payload and returns the bare ASC. In the `AudioEncoder` output callback, when the
description is a wrapped descriptor (Safari), pass mp4-muxer the extracted bare ASC so the
esds is wrapped exactly once. Chrome already provides a bare ASC (starts with the AOT
bits, not a descriptor tag) → returns null → metadata passed through unchanged. Frontend-
only change; no Rust touched.

### Verification of the fix
- Unit: ran the extractor on Safari's actual description bytes → `0x1190` (AAC-LC/48k/
  stereo); bare ASC input → null (pass-through). `npx tsc -b`: no errors in the file.
- Muxer-level repro with the REAL mp4-muxer + Safari's real bytes: old path (full
  descriptor) reproduced the exact failure ("object type 0, 22050 Hz, 0 channels"); new
  path (extracted ASC) produced a track ffmpeg reads as `aac (LC) 48000 Hz stereo` and
  Apple CoreAudio opens (`2 ch, 48000 Hz, aac`).
- **End-to-end (real app):** new recording `recording_20260613_161021.mp4` (23.7MB,
  16.49s). Audio now decodes: ffmpeg `aac (LC), 48000 Hz, stereo`; `afinfo` opens it;
  full-track decode with zero errors; real signal (mean −46 dB / max −23 dB, 1.57M
  samples), not silence. Video composite still correct (2560x1440, H.264 Baseline,
  ~48.8 fps — user picked a higher target this run; minor drops via backpressure, no
  regression). **Audio esds bug fixed and confirmed.** Nothing committed.

## DTS "issue" investigated — it was a measurement artifact (CORRECTION)

Followed up on the "video DTS collisions" noted above and **corrected the earlier
finding**: the recordings were never malformed. The container DTS is strictly
monotonic in every file checked:
- File 155040 (pre-audio-fix): isolated video track → 0 non-increasing of 399 packets,
  min gap 576 ticks (~10ms). `ffmpeg -c copy -f null` → 0 warnings.
- File 162933 (post-audio-fix): 0 non-increasing of 1329 packets, min gap 518 ticks
  (~9ms). `ffmpeg -c copy -f null` → 0 warnings.

The "165 / 146 non-monotonic DTS" warnings came from `ffmpeg -f null` WITHOUT `-c copy`:
that decodes the video and re-derives DTS in a coarse constant-frame-rate output
timebase, which collapses neighbors for variable-frame-rate content (the warning values
are tiny integers like `5 >= 5`, not the real 57600-scale DTS). Real players read the
container DTS and were always fine. Diagnostic lesson: use `-c copy -f null` or read
`packet=dts` directly to judge a file's DTS; plain `-f null` re-derives and lies for VFR.

Implemented a defensive timestamp clamp (strictly-increasing, +100us floor) and proved
via simulation it would prevent collisions in a true sub-tick burst — but since no real
file ever exhibited the problem (min gaps were ~9-10ms, nowhere near a tick), **reverted
it** per the user's preference for surgical changes (`git checkout HEAD -- recording-
canvas.tsx`). The audio esds fix (committed in 2d9ae6c) is unaffected and still verified.

### State
recording-canvas.tsx back to the committed version (audio fix intact, no DTS change).
Nothing new committed this round. Open follow-up unchanged: AAC bitrate cap (~130k vs
configured 256k).

## Feature: live audio monitor (meter + waveform) in the Audio Track section

User asked to add monitoring graphics to the timeline's Audio Track section, live
before AND during recording (Option A). Built it DECOUPLED from the recording pipeline
so the just-verified recording path is untouched.

### Changes
- NEW `hooks/use-audio-monitor.ts`: `useAudioMonitor(enabled)` opens its OWN default-mic
  stream (same constraints as recording: no DSP, stereo, 48k) + an AudioContext, and
  exposes `analyserL`/`analyserR` (per-channel meter) and `analyserMix` (waveform).
  Active whenever `externalConfig.captureMic` is on. Resumes a suspended context and
  retries once on the next user gesture. Teardown stops the stream + closes the context.
- NEW `components/asmr-recorder/audio-monitor-graphics.tsx`: `StereoMeter` (L/R bars,
  peak-hold, clip light) and `LiveWaveform` (oscilloscope), both throttled to ~30fps.
- `recording-context.tsx`: runs the monitor, exposes `audioMonitor` on the context.
- `timeline.tsx`: meter in the Audio Track label, waveform across its lane.

### Review (6-dimension workflow, 34 agents) + fixes applied
Adversarial review confirmed 17 findings; after verifier triage most were
clarity/design-preference. Fixed the real ones:
- HIGH (mono mic): WebKit doesn't reliably honor channelCount:2 and built-in mics are
  often mono — a mono source through ChannelSplitter(2) leaves the R meter dead. Now
  reads getSettings().channelCount; uses the splitter only when stereo is confirmed,
  otherwise mirrors the mono signal to both meters. Added settings/sample-rate warnings.
- dBFS formula clarified `(db - FLOOR)/(0 - FLOOR)`; waveform explicitly recentered on 128.
Deliberately NOT changed (with reasons): captureMic default stays true (mic-on is correct
for ASMR + controls recording, not just the monitor; the mount-time mic prompt is
pre-existing via fetchBrowserDevices); StrictMode double-open (dev-only, cancelled+teardown
already correct); clip threshold 0.99 (verifier confirmed it's ~-0.09 dBFS, a sensible
near-clip warning); two-stream contention (WebKit allows it, keeps recording decoupled/safe).

### Verification
`npx tsc -b`: no new errors (only the pre-existing SectionConfig-unused in
recording-context.tsx). `npx vite build`: succeeds. NOT yet runtime-tested — the meter/
waveform are visual and need a manual check (reload, watch the Audio Track section move

### Known tradeoff (later RESOLVED — see "Gate the mic indicator" below)
With captureMic on, the monitor holds the mic open whenever the app is open (macOS mic
indicator stays lit). Inherent to live-before-record monitoring; can be gated differently
if undesired.

### Follow-up: waveform not visible (fixed)
User reported the meter worked but the waveform was missing. Diagnosed via a temporary
size log: canvas was 1200x47 and the analyser was live — so it WAS rendering, the wave was
just too small to see. Two causes: (1) `getByteTimeDomainData` only has 256 coarse levels,
so quiet ASMR barely deviates from center; (2) no vertical gain, so a quiet signal was a
1-2px wiggle. Fix: switched to `getFloatTimeDomainData` and added auto-gain (scale to the
recent peak, fast attack / slow release, floored at -30 dBFS so silence/noise isn't blown
up to full scale) so the wave fills ~85% of the lane at any level. Also made the canvas
size its buffer to the lane (DPR-aware via ResizeObserver) and render `block` with a faint
tint. The waveform now shows shape/activity (auto-gained); the meter remains the
absolute-level reference.
