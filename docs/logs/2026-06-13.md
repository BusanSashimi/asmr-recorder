## Stage A optimization of the 4-way split recording pipeline

### Context / investigation
Asked to find a more optimal way to record the 4-way (2x2) split screen, starting
from `ai-dev/dev-logs/fixing-screen-recording-issue.md`. Key reframe: that dev log

release builds (the `ffmpeg` cargo feature is only enabled by `dev.sh`). The actual

section rAF crop canvases) → `recording-canvas.tsx` (2D-canvas composite + WebCodecs

Ran a multi-agent audit + adversarial verification. Findings & recommended path

- H.264 `avc1.42001f` (Baseline L3.1) does **not** break recording at 1440p60 —
  WKWebView/VideoToolbox uses the string only to pick the profile and applies
  `Baseline_AutoLevel`, so it encodes fine. Baseline *profile* is only a ~10-20%
  efficiency nicety, not a functional bug.
- `autoGainControl:false` is **not honored** by WebKit (bug 204444 still open);
  `channelCount:2` is unreliable on macOS Safari. `echoCancellation:false` (and
  effectively `noiseSuppression`) **are** honored.

### What was verified
Inspected the first real recording (`test-results/recording_20260613_155040.mp4`).
- **Video PASS:** correct 2x2 composite (screen top-L/R, webcam bottom-L/R), 2560x1440,

  visually-correct output.
- **Audio FAIL (root-caused):** the AAC track was undecodable — ffmpeg AND Apple
  CoreAudio (`afinfo`) both refused it ("Audio object type 0… 22050 Hz, 0 channels").
  Parsed the raw MP4 boxes: the `mp4a` header was correct (2ch/48kHz) and the real
  AudioSpecificConfig `0x1190` (AAC-LC/48k/stereo) was present **but buried one level too
  deep** — the `esds` was double-wrapped. Root cause: WKWebView/Safari's `AudioEncoder`
  emits `decoderConfig.description` as a full MPEG-4 ES_Descriptor, and mp4-muxer wraps
  whatever it's given in its own DecoderSpecificInfo (confirmed in mp4-muxer source:
  `esds` writes `description` verbatim as the tag-0x05 payload). So a standards parser
  reads the top byte (0x03) as audioObjectType → 0 → undecodable. Structural, independent
  of channel count/bitrate → NOT caused by the Stage A audio constants; it was latent.

### Fix (`frontend/src/components/asmr-recorder/recording-canvas.tsx`)
Added module-level `extractAudioSpecificConfig(description)`: walks the MPEG-4 descriptor
tree (ES_Descriptor 0x03 / DecoderConfigDescriptor 0x04) to the DecoderSpecificInfo
(0x05) payload and returns the bare ASC. In the `AudioEncoder` output callback, when the
description is a wrapped descriptor (Safari), pass mp4-muxer the extracted bare ASC so the
esds is wrapped exactly once. Chrome already provides a bare ASC (starts with the AOT
bits, not a descriptor tag) → returns null → metadata passed through unchanged. Frontend-
only change; no Rust touched.

### Verification of the fix
- Unit: ran the extractor on Safari's actual description bytes → `0x1190` (AAC-LC/48k/
  stereo); bare ASC input → null (pass-through). `npx tsc -b`: no errors in the file.
- Muxer-level repro with the REAL mp4-muxer + Safari's real bytes: old path (full
  descriptor) reproduced the exact failure ("object type 0, 22050 Hz, 0 channels"); new
  path (extracted ASC) produced a track ffmpeg reads as `aac (LC) 48000 Hz stereo` and
  Apple CoreAudio opens (`2 ch, 48000 Hz, aac`).
- **End-to-end (real app):** new recording `recording_20260613_161021.mp4` (23.7MB,

## DTS "issue" investigated — it was a measurement artifact (CORRECTION)

Followed up on the "video DTS collisions" noted above and **corrected the earlier
finding**: the recordings were never malformed. The container DTS is strictly
monotonic in every file checked:
- File 155040 (pre-audio-fix): isolated video track → 0 non-increasing of 399 packets,
  min gap 576 ticks (~10ms). `ffmpeg -c copy -f null` → 0 warnings.
- File 162933 (post-audio-fix): 0 non-increasing of 1329 packets, min gap 518 ticks
  (~9ms). `ffmpeg -c copy -f null` → 0 warnings.

The "165 / 146 non-monotonic DTS" warnings came from `ffmpeg -f null` WITHOUT `-c copy`:
that decodes the video and re-derives DTS in a coarse constant-frame-rate output
timebase, which collapses neighbors for variable-frame-rate content (the warning values
are tiny integers like `5 >= 5`, not the real 57600-scale DTS). Real players read the
container DTS and were always fine. Diagnostic lesson: use `-c copy -f null` or read
`packet=dts` directly to judge a file's DTS; plain `-f null` re-derives and lies for VFR.

Implemented a defensive timestamp clamp (strictly-increasing, +100us floor) and proved
via simulation it would prevent collisions in a true sub-tick burst — but since no real
file ever exhibited the problem (min gaps were ~9-10ms, nowhere near a tick), **reverted
it** per the user's preference for surgical changes (`git checkout HEAD -- recording-
canvas.tsx`). The audio esds fix (committed in 2d9ae6c) is unaffected and still verified.

## AAC bitrate cap: force CBR (fixed + verified)

The recorded audio read ~76-130k despite the configured 256k. Root cause: WebKit's AAC
encoder defaults to VBR, treating `bitrate` as a loose ceiling, so quiet ASMR content
encoded far below it. Fix (recording-canvas.tsx): request `bitrateMode: "constant"` in
audioEncoder.configure, wrapped in a try/catch that falls back to the default-mode config
if CBR is rejected (so it can't break the verified audio path or trigger the WebM
fallback). Verified end-to-end: recording_20260613_194302.mp4 audio is now
`aac (LC), 48000 Hz, stereo, 256 kb/s` (measured), packets tight (avg 683B), still decodes
cleanly (esds fix intact). Tradeoff: CBR means larger files / "wasted" bits in quiet
passages, but guaranteed headroom — appropriate for ASMR.

## Simple cut/trim editor for recorded video (research + implement)

### Research (web + adversarial verification)
Asked to "add a simple cut edit function" and analyze the optimal implementation via web
search. Ran a research workflow over 5 candidate approaches (frontend WebCodecs+mp4box.js,
FFmpeg sidecar, ffmpeg-next Rust crate, ffmpeg.wasm, UX/precedent) + adversarial verification
of the decision-driving claims. Key findings:
- `-c copy` (any toolchain) is NOT frame-accurate — snaps to keyframes. The recorder's old
  KEYFRAME_INTERVAL=120 frames meant copy-cuts snapped to ~2-2.4s.
- ffmpeg.wasm SharedArrayBuffer objection was REFUTED (single-thread core needs none), but
  it's rejected anyway on bundle size (~25-32MB) + 5-20x slowness.
- FFmpeg sidecar: 40-80MB/platform + GPL source-offer obligation. ffmpeg-next: current
  /opt/homebrew dynamic link isn't distributable.
- **mp4-muxer@5.2.2 (the recorder's muxer) is DEPRECATED in favor of Mediabunny** (same
  author, Vanilagy). Mediabunny does demux+mux+trim in one ~5kB zero-dep (MPL-2.0) lib.

### Decision (user-chosen scope)
Lossless + instant trim, head/tail only, opens right after recording on the in-memory bytes.
Implemented as a frontend Mediabunny **packet-copy transmux** (no decode/re-encode):
EncodedPacketSink.getKeyPacket() snaps the cut-in to the keyframe at/before the chosen time,
copies encoded packets verbatim to EncodedVideoPacketSource/EncodedAudioPacketSource, rebases
timestamps to origin=min(videoKeyframe, audioStart) to avoid negative ts. avc1.42001f is
Constrained Baseline (no B-frames) so the tail can stop on any frame.
**Verified in Node (no WebCodecs present) against a real recording: lossless, ~14ms, valid
playable MP4 — proving it's a true transmux with NO VideoDecoder dependency (so no macOS
13.3 floor, works everywhere).**

### Changes
- `recording-canvas.tsx`: KEYFRAME_INTERVAL=120 -> KEYFRAME_INTERVAL_SECONDS=1 (computed
  from fps in the encode loop) for ~1s keyframe spacing -> tighter cut-in snap. After
  finalize, dispatch `recordingReadyForEdit` CustomEvent with the in-memory MP4 Blob (only
  the WebCodecs/MP4 path; WebM fallback never opens the editor). Original auto-save untouched
  (non-destructive — trim saves a separate file via existing save_media_recording).
- `lib/utils.ts`: added `arrayBufferToBase64` (chunked) for the save path.
- `trim-editor.tsx` (NEW): dialog with <video> preview, dual-handle radix slider (in/out),
  range-limited preview playback, Mediabunny packet-copy export.

## Harden two latent audio bugs in the recording pipeline

Reviewed the latest dev log, confirmed the working tree was clean (all prior work committed via
PR #1 + the tsc-error fix), and surfaced open follow-ups. User chose to fix the two latent audio
bugs the earlier sessions had flagged as "worth a follow-up." Both confirmed present in the
committed `recording-canvas.tsx` before editing. All changes are in that one file.

### Bug 1 — sample-rate divergence (could pitch-skew / break audio)
`AudioData` was stamped with the live `inputBuffer.sampleRate` while the encoder + muxer were
hard-coded to `AUDIO_SAMPLE_RATE` (48k). If WebKit clamps the AudioContext to the hardware rate
they diverge → pitch-skew or undecodable track. The old `startAudioProcessing` even recreated the
context on mismatch, which on WebKit just re-clamps (ineffective) and could desync further.
- Added `ensureAudioContext()` — one source of truth that creates (at 48k) or reuses the existing
  context (incl. the multi-stream mixing context `acquireAudioTrack` makes at line ~527).
- `initializeWebCodecs` now reads the context's **actual** `sampleRate` and configures BOTH the
  AAC encoder AND the muxer audio track to that rate. `startAudioProcessing` reuses the same
  context (removed the recreate-on-mismatch block) → `AudioData` rate == encoder rate == mp4a/esds
  rate in every path (single stream, multi-stream mix, clamp). Logs a warning when clamped.

### Bug 2 — an audio-config failure killed the whole video path
A failing `audioEncoder.configure()` propagated to the outer catch → silent WebM (MediaRecorder)
fallback, losing a perfectly good video pipeline. Now audio setup is isolated in its own
try/catch: on failure it logs, closes the partial encoder, sets `hasAudio=false`, and the muxer is
built WITHOUT an audio track → recording continues as a **video-only MP4**. The outer catch now
only fires for genuine video failures. The esds-extraction fix and the CBR→default bitrate
fallback are preserved exactly.

### Reorder consequence + review
Bug 1's fix required moving audio setup BEFORE `encoder.configure()` (must know the real rate
first). Ran a 4-dimension adversarial review workflow (19 agents, 15 findings → 14 refuted on
verification, 1 confirmed). Confirmed (low): a VIDEO-config failure after audio setup now orphans
the configured `audioEncoder` (its ref isn't assigned yet, so the outer catch / teardown can't
close it) — JS-only, no mic/OS leak (stream + context are torn down unconditionally). **Fixed**:
hoisted the `audioEncoder` declaration above the try and added `audioEncoder?.close()` in the
outer catch. The other 14 (TDZ on the muxer closure ref, double-create, deps, mic leak, etc.) were
verified non-issues.
